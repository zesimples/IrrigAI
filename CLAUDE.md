# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

IrrigAI is a precision-irrigation decision-support platform. A **deterministic agronomic engine** computes water-balance recommendations (ET₀, crop demand, drainage thresholds, dosage); an **LLM explanation layer** (OpenAI GPT-4o-mini) converts those recommendations into natural-language explanations — the LLM never makes agronomic decisions. A background **ingestion worker** pulls probe readings and weather data from external providers on a schedule.

## Development commands

All commands assume Docker Compose is running. Run them from the repo root.

```bash
make dev              # Start all services with hot-reload
make down             # Stop services
make down-v           # Stop and remove volumes (fresh DB)

make migrate                      # alembic upgrade head (inside container)
make makemigration msg="<text>"   # autogenerate migration from model changes

make test-backend     # pytest -v inside container
make test-frontend    # cd frontend && npm run test:run (Vitest)
make test-e2e         # Playwright E2E (requires running stack)

make lint             # ruff check + ruff format --check
make format           # ruff format (auto-fix)
make seed             # seed DB with test data (dev login: you@irrigai.dev / irrigai-dev)
make shell-backend    # bash inside backend container
make logs-backend     # follow backend logs
```

**Run a single backend test:**
```bash
docker compose exec backend pytest tests/test_engine/test_water_balance.py -v
# or locally:
cd backend && pytest tests/test_engine/test_water_balance.py -x -q --tb=short
```

**Local backend (outside Docker):**
```bash
cd backend && pip install -e ".[dev]"
export DATABASE_URL=postgresql+asyncpg://irrigai:irrigai_dev@localhost:5434/irrigai
export DATABASE_URL_SYNC=postgresql://irrigai:irrigai_dev@localhost:5434/irrigai
```

**Production deploys:**
- Backend-only changes: `git pull && docker compose up -d --build backend` (and `--build worker` if engine/scheduler code changed). The `backend`/`worker` services bake code into the image at build time — there is **no source volume mount** in production — so `docker compose restart` runs the *old* image and silently serves stale code. Always rebuild.
- Frontend changes: `git pull && docker compose up -d --build frontend`
- Schema changes: run `make migrate` after pulling. **Run the migration BEFORE (or as part of) swapping the new image, not after** — if the new backend/worker image starts serving while its migration is unapplied, code that queries a not-yet-created table 500s every request until you migrate (this happened on the dose-do-dia rollout: `relation "irrigation_fingerprint" does not exist` on every recommendation + calibration). Safe sequence when the host has no `make` (or generally): `git pull && docker compose build backend worker frontend && docker compose run --rm backend alembic upgrade head && docker compose up -d backend worker frontend`. (`make migrate` is just `docker compose exec backend alembic upgrade head`.)
- **Current production host uses THREE compose files** — merge `docker-compose.yml`, `docker-compose.prod.yml`, and the production-local/untracked `docker-compose.caddy.yml` for every build, migration, recreate, exec, log, and status command. The host runs **systemd Caddy** on ports 80/443; `docker-compose.caddy.yml` publishes only `127.0.0.1:8000:8000` and `127.0.0.1:3000:3000` for Caddy. Omitting it during `up` removes those publications and causes public 502s. Do not start the committed Compose nginx/certbot services on this host, and do not use `--remove-orphans` because `irrigai_grafana` and `irrigai_prometheus` belong to the deployment. Public URL: `https://irrigai.95.111.254.42.nip.io`. Standard sequence: build `backend worker frontend`; run `alembic upgrade head`; then `up -d --no-deps backend worker frontend` with all three files. Dev hot-reload mounts come from `docker-compose.dev.yml` (`make dev`); a stack started with plain `docker compose up` bakes code at build time for backend AND frontend — rebuild to pick up new code.

## Architecture

```
PostgreSQL 16 + TimescaleDB   ←  probe readings time-series
Redis 7                        ←  job locks, rate-limit counters
APScheduler (worker container) ←  periodic ingestion + recommendation jobs
FastAPI (backend container)    ←  REST API at /api/v1
Next.js 14 (frontend container)←  App Router UI, proxies /api/v1 → backend
```

### Backend (`backend/app/`)

| Directory | Purpose |
|-----------|---------|
| `engine/` | **Deterministic agronomic engine** — water balance, ET₀, crop demand, dosage, stress projection, trigger logic. Entry point: `engine/pipeline.py` (`RecommendationPipeline`). Also `soil_water_model.py` + `soil_water_data.py`: a rain-anchored FAO-56 running balance that, for **probe-less sectors that have a flowmeter**, replaces the static 70%-of-TAW seed using measured irrigation + weather history (probes stay authoritative elsewhere). Every parameter comes from DB records, never hardcoded. |
| `ai/` | **LLM explanation layer** — `assistant.py` orchestrates context → prompt → LLM; `context_builder.py` fetches all DB context before calling the LLM; `prompt_templates.py` defines structured output schemas; `probe_signal.py` computes signal statistics (flatline, drainage events). |
| `adapters/` | **Provider abstraction** — `factory.py` selects mock/irriwatch/myirrigation at runtime via `PROBE_PROVIDER` / `WEATHER_PROVIDER` env vars. All adapters implement the interface in `base.py`. |
| `api/v1/` | REST endpoints grouped by resource (farms, plots, sectors, probes, recommendations, chat, …). Unified by `router.py`. |
| `models/` | SQLAlchemy 2.0 async ORM models. |
| `schemas/` | Pydantic v2 request/response schemas, including `schemas/ai.py` for structured LLM output. |
| `alerts/engine.py` | Alert generation from recommendation state changes. |
| `anomaly/` | Rule-based anomaly detection on probe readings. |
| `services/scheduler.py` | APScheduler jobs (data + flowmeter ingestion, daily recommendations, alert check, reference recompute). Redis locks (`job_lock.py`) prevent duplicate runs. Per-farm jobs run through `_run_per_farm_job` → `classify_per_farm_run` records `success` / `partial_failure` / `failure` (an all-farms-failed run no longer logs "success") plus the `scheduler_farm_failures_total` metric. Stamps a Redis liveness heartbeat (`app/heartbeat.py`) on startup and after every job. |
| `access.py` | Per-tenant authorization controller — see **API security** below. |

**AI structured output flow:**
1. `IrrigationAssistant` (in `ai/assistant.py`) calls `context_builder` → builds `AgronomicInterpretation` (Pydantic schema in `schemas/ai.py`) via structured OpenAI output.
2. `render_structured(interpretation)` converts the structured output to `• Label: Value` bullet lines for the frontend.
3. Frontend `parseResultBullets()` in `SectorAnalysis.tsx` parses these bullets into the styled card UI.

**Structured-output PT contract (`_complete_structured`):** every card endpoint routes through `assistant._complete_structured`, which appends `prompt_templates.get_structured_output_contract(language)` to the system prompt before calling `client.complete_structured` (native `beta.chat.completions.parse`). The contract forces the model to (a) fill **all** fields in European Portuguese — translating any English context values (e.g. the engine's "No sector crop profile attached") — and (b) set `evidence[].source` to **canonical context paths** (`water_balance`, `recommendation_history`, `weather.forecast`, `probe_signal`, `known_limitations`, …) that `render_structured`'s `_SRC_LABEL` maps to PT labels. This restores guidance that lived in the deleted `STRUCTURED_OUTPUT_PT`: the native-`.parse` migration dropped it, and the schema (`schemas/ai.py`) has no field descriptions, so without the contract the model returned English fields and invented source paths (e.g. `sectors.recommendation_action`) that rendered as raw bullets like "Sectors Recommendation Action: irrigate". CI uses the mock client, which does not exercise real `.parse` language behavior — so regressions here surface only under `LLM_PROVIDER=openai`.

**Probe-pattern interpretation guard:** `probe_signal.py` attaches the sector's `latest_recommendation` (engine action + `depletion_pct`) to the signal stats. After the LLM returns, `assistant._apply_probe_recommendation_guard()` deterministically overrides the advice when the engine reports no deficit (`action` ∈ {`skip`, `defer`} or `depletion_pct ≤ 5%`) — it forces `risk_level=low`, monitoring-only actions, and injects the engine evidence. This enforces the rule that the LLM never overrides the deterministic engine: an isolated "humidade crítica" depth is treated as a possible sensor discrepancy, not a reason to irrigate. Note: the engine reports "don't irrigate" via `RecommendationAction.skip` / `.defer` (see `core/enums.py`) — there is no `no_irrigation` value.

**Soil-water source (`swc_source`):** the pipeline records how rootzone SWC was obtained on each recommendation — `probe_weighted` (probe, authoritative), `water_balance_model` (the FAO-56 model for probe-less + flowmeter sectors), or `default_estimate` (static 70%-of-TAW seed). Surfaced in `Recommendation.inputs_snapshot` (`swc_source` + `swc_model` metadata). The model never runs when a probe is present, and degrades to the static seed on any error (per-sector try/except).

**Probe soil calibration ("Calibração AI"):** `engine/auto_calibration.py` derives a sector's CC (`observed_fc`) and effective refill line (`observed_refill`) **deterministically** from the probe's own VWC envelope (cycle-based, else percentile envelope) — *no LLM decides soil numbers* (the button label is user-facing only). `ProbeCalibrationService.compute_and_save` upserts one `probe_calibration` row per sector. `pipeline.resolve_sector_soil_bounds` is the single resolver shared by the engine and the probe chart (`api/v1/probes`), so CC/PMP reference lines can't diverge from the FC the engine uses. Calibration window is `CALIB_WINDOW_DAYS = 30`. The readings endpoint additionally computes **display-only per-depth envelopes** (`compute_depth_envelope`, same percentile+plausibility logic per depth, 30-day window) onto `DepthReadings.field_capacity/wilting_point` — display-only, suppressed under `scp_override`, never feeds the engine's TAW. (The Soma chart that used to sum these bounds was removed 2026-07-15 — the replacement "Zona radicular" chart uses the sector-resolved CC/PMP directly; see **Rootzone chart** below.) Precedence (`engine/soil_bounds.resolve_soil_bounds`, pure/unit-tested): `scp_override` (customized) > `probe_calibrated` > `scp` > `plot_preset` > `default`.
- **Recency rule (last action wins), enforced at the API layer, not the resolver:** `POST /sectors/{id}/auto-calibration/run` clears the sector's `SectorCropProfile.is_customized` so a fresh calibration takes precedence; a later manual soil/CC-PMP edit (`PUT /sectors/{id}/crop-profile`) re-sets `is_customized=True` and overrides the calibration again. The pure resolver always treats `is_customized` as authoritative — the clearing/setting lives in those two endpoints.
- **Staleness:** `CALIB_MAX_AGE_DAYS=90`; `is_calibration_stale(computed_at)` makes the resolver ignore an old calibration (falls through to the next source) while still surfacing its metadata as `used=False/stale=True`. Solved in code via `computed_at` — no schema column.
- **`/run` response + UI feedback:** returns `observed_*`, effective `previous_*`/`effective_*` bounds, `changed`, `applied`, `cleared_customization`. The `AiCalibrationButton` toast reports the real CC transition ("CC 17→24") and always refreshes the probe chart (`ProbeReadingsInline` `refreshTrigger`); the recommendation regenerates only when the effective bounds moved.
- **Tension/Watermark sectors can't calibrate** (the model needs `vwc_m3m3`, not `soil_tension_cbar`): `/run` returns a specific 422 (`diagnose_unavailable`), and the sector-status `calibration_available` flag disables the button (tooltip) for them. At Herdade do Esporão only the Olival (olive) sectors are Watermark; everything else is VWC.
- **Immutable calibration history (2026-07-15):** every deterministic computation is recorded as a `ProbeCalibrationRun` row (`models/probe_calibration_run.py`). **The weekly scheduler creates `candidate` runs only — unless the farm has opted into auto-apply** (`Farm.calibration_auto_apply`, default `false`; see **Calibration auto-apply** below), in which case it may promote its own runs through the gate. On a non-opted-in farm the behaviour is unchanged: it never touches live soil bounds. A manual `/run` is computed, recorded, and applied in one step. `POST /calibration-runs/{run_id}/apply` promotes a candidate: it marks the previously-applied history row `superseded`, updates the `probe_calibration` projection that `resolve_sector_soil_bounds()` reads, clears conflicting manual soil customization (`is_customized`), and is audited. History: `GET /sectors/{sector_id}/calibration-runs`. The LLM still never chooses FC/refill values.

**Calibration auto-apply (2026-07-28, per-farm opt-in, default OFF):** the weekly `probe_calibration` job may apply its own deterministic results on farms whose `Farm.calibration_auto_apply` is true (toggled from the **farm-selection dashboard** — each farm card carries a calibration strip with the on/off switch and a *correr* button that runs the sweep on demand; also still settable via `PUT /farms/{farm_id}`). Motivation was **coverage**, not freshness: sectors whose preset FC sits below the probe's real VWC envelope are clamped to ~0% depletion and told "never irrigate" until a human clicks per sector (77 at Innoliva), so the calibration that would fix them was computed weekly and discarded.
- **The gate is pure and deterministic** (`engine/calibration_policy.py` `evaluate_auto_apply`, same idiom as `engine/soil_bounds.resolve_soil_bounds` — no DB, no I/O, table-driven unit tests). First match wins: `manual_override` → `probe_stale` (>`PROBE_VERY_STALE_H`, or a missing `last_reading_at`) → `flatline` (**all** judgeable depths below `AUTO_APPLY_FLATLINE_STD_M3M3`; one flat *deep* depth is normal, not a fault) → `delta_exceeds_cap` (>`AUTO_APPLY_MAX_DELTA_M3M3` = 0.05, exclusive) → `applied`. Plausibility and the 48-reading floor aren't re-checked here: `compute_sector_calibration` returns `None` instead of an implausible result, counted as `no_candidate`.
- **Both gate inputs key on the RESOLVED source, never on raw DB flags** — `before.source == "scp_override"` and `== "probe_calibrated"` (named `SOURCE_*` constants in `soil_bounds`). This is load-bearing, and the reason is non-obvious: `PUT /crop-profile` sets `is_customized=True` on *any* edit while the resolver honours `scp_override` only when **both** soil bounds are non-null, so gating on the raw flag made a `mad` edit block a clamped sector forever; and gating on "a `probe_calibration` row exists" ignored that the resolver *discards* a >90-day-stale calibration, so the cap measured movement against a preset and could only get staler. **Don't "simplify" these back to the flags.**
- **First-ever application is deliberately uncapped.** With no prior probe-derived value, `before` is an unmeasured soil-texture lookup — a large distance means the *preset* is wrong (the clamp bug), not that the measurement is anomalous. The cap guards drift from a trusted value, which presupposes one exists.
- **The invariant:** the auto path **never writes `SectorCropProfile.is_customized`** — both manual endpoints deliberately clear it ("last action wins"), so copying that pattern here would silently destroy agronomists' edits farm-wide. There is a dedicated regression test.
- **Blocked candidates persist nothing** (no history row, no projection change), so logs and metrics are the only trace: per-sector INFO/WARNING with both value pairs from `ProbeCalibrationService._record_outcome`, a per-farm summary from `scheduler._calibration_sweep_for_farm`, and `irrigai_calibration_auto_apply_total{result,reason,method}` where `result="no_candidate"` is the coverage number to watch (tension/Watermark sectors sit there permanently and correctly). Side effects fire only **after** the sector's savepoint releases, so a rolled-back sector can't log "applied".
- **Each sector runs in `db.begin_nested()`.** This fixed a real pre-existing bug: the old `try/except` wrapped `db.add()` + `flush()`, and a failed flush leaves an async session needing rollback, so one bad sector raised `PendingRollbackError` on every later sector. `compute_all_for_farm` now returns `CalibrationSweepCounts` (applied/skipped/no_candidate/candidates/failed) so an all-sectors-failed farm can't log clean.
- No recommendation regeneration: calibration runs Mon 04:00 UTC, `daily_recommendations` at 05:00 UTC. Spec/plan: `docs/superpowers/specs/2026-07-28-calibration-auto-apply-design.md` (carries an **Amendment** section recording the resolved-source change) and `docs/superpowers/plans/2026-07-28-calibration-auto-apply.md`.
- **Manual sweep:** `POST /farms/{farm_id}/calibration-sweep` (`api/v1/auto_calibration.py`, `3/minute`) runs the scheduler's own sweep for one farm on demand and **honours that farm's flag** — with the flag off it records candidates and moves no bounds, so it doubles as a safe preview of what Monday will do. It returns the counts plus a `SectorSweepOutcome` per sector (reason, and `fc_before`/`fc_candidate` even for blocked sectors), which is how blocked reasons reach the UI at all — they persist no DB row. Audited as `probe_calibration_sweep_triggered` with the real `user_id`, unlike the scheduler's `user_id=NULL` rows. Synchronous: tens of seconds on Innoliva's 77 sectors.

**Dose do dia (dose-centric recommendation):** the headline is a 4-band dose (`reforcada`/`normal`/`curta`/`pode_saltar` — `engine/dose_presentation.py`), not a binary verdict; dosage is computed on **every** pipeline run (reserve days get a reduced dose). Dose source precedence (mirrors `swc_source`, stored in `inputs_snapshot`): `configured` (application rate/emitters) > `probe_learned` (per-sector `irrigation_fingerprint` learned weekly from probe-detected irrigation events, 25-day window/staleness, ≥3 usable events, VWC-only) > `mm_only`. `RecommendationAction` (irrigate/skip/defer) is unchanged underneath — alerts and AI guards still key off it. The Step 11.6 fingerprint lookup is **savepoint-isolated** (`pipeline._load_sector_fingerprint`) — a DB error there (e.g. the `irrigation_fingerprint` migration lagging a deploy) degrades the dose to `mm_only` and increments `dose_fingerprint_lookup_failures_total` instead of 500-ing the whole recommendation. **Any crop-profile edit regenerates the recommendation:** `PUT /sectors/{id}/crop-profile` calls `generate_recommendation` on any actual edit — every updatable field feeds the engine (soil bounds → depletion, `mad` → RAW threshold, root depths → rootzone weighting, `stages` → Kc) — best-effort (rolls back + returns the saved profile on failure), so the displayed rec isn't frozen until the next scheduler run. Plot propagation stays scoped to the soil-bounds fields.

**Rootzone chart (replaced "Soma", 2026-07-15 `6815755`):** depletion is computed from the **root-zone-weighted** SWC (`probe_interpreter._compute_rootzone`, sensors with `depth_cm <= effective_root_depth`). The old "Soma" view summed **all** depths, so a dry root zone under a wet subsoil read 82% depletion while Soma looked green — recurring confusion, structurally closed by replacing Soma with a **"Zona radicular"** view (`ProbeSumChart.tsx` — filename kept): it plots the backend's `rootzone_swc` series (engine-weighted `probe_interpreter.weighted_rootzone_series`, served by `api/v1/probes`) against the sector-resolved CC/PMP, and computes depletion/available-water in the frontend with the exact engine formula (clamp VWC to [PMP, CC], `(CC − clamped)/(CC − PMP)`), so the chart's "Depleção da sonda" card numerically matches the recommendation. The "Profundidades" view keeps the per-depth lines plus the same rootzone overlay; the rootzone line's timestamps are built from the already-downsampled per-depth points so they can't phase-drift under an interval. Effective root depth (young/mature by tree age, then phenological-stage override) is resolved by the shared `pipeline.resolve_effective_root_depth_m` so the chart and engine never diverge (same idiom as `resolve_sector_soil_bounds`). When no sensor is in the root zone, both the engine and the overlay fall back to weighting all depths. The real lever when a dry-rootzone call looks wrong is the **crop profile's stage root depth** (agronomic), not code.

**Probe staleness thresholds live in `engine/staleness.py`** (single source of truth): `PROBE_STALE_H = 30`, `PROBE_VERY_STALE_H = 72`. Daily-publishing providers (MyIrrigation/iMetos) deliver ~daily, so the old 6h cutoff flagged nearly every such sector stale (confidence → "média", spurious connectivity alerts). Tiers: fresh ≤30h, stale 30–72h, dead/forecast-only >72h. All probe-staleness consumers import from here — `confidence.py` (penalty + `source_confidence`), `probe_interpreter.STALE_THRESHOLD_H`, `alerts/engine.py` (connectivity alert fires at 72h, not 6h), `ingestion._derive_data_status` (per-depth `data_status`, which feeds the AI `known_limitations`). Weather staleness (`WEATHER_STALE_H`) is a separate knob.

**Probe `external_id` ↔ MyIrrigation device:** `external_id` is `"{project_id}/{device_id}"` (e.g. `1597/9287`). When a device is **renamed in the MyIrrigation portal its `device_id` changes**, so our stored `external_id` 404s and that sector silently stops ingesting (the in-app sector rename is harmless — it only changes `Sector.name`). Fix is a DB update of `Probe.external_id` (keep the project prefix, swap the device id); `last_reading_at` left as-is auto-backfills the gap (adaptive lookback caps at 168h). There is no UI to edit `external_id` yet.

**Per-farm MyIrrigation credentials:** stored **encrypted** in the `farm_credentials` table (`EncryptedString`), overriding the global `MYIRRIGATION_*` env vars per farm. Since 2026-07-15 there IS an API: `GET/PUT /farms/{farm_id}/credentials` (responses expose only configuration/status metadata — **never return stored passwords, tokens, or client secrets**) plus `GET /farms/{farm_id}/provider-resources` (connection test + project/device discovery, also secret-free), both used by the onboarding wizard. `scripts/set_farm_credentials.py` remains for ops use (env-driven, prints no secrets, `VERIFY=1` replays a real device-data call). The 406 "Client Signature Invalid" outage was a wrong stored credential, not a code bug. The Fernet key comes from `ENCRYPTION_KEY` (see below) — **changing it makes existing ciphertext undecryptable** (`decrypt()` returns `None`, not an error), so keep it stable or re-run `set_farm_credentials.py` after a rotation. `farm_credentials` also holds a plaintext `weather_device_id` and (since the Innoliva onboarding) a plaintext `project_id`; `adapters/factory._get_myirrigation` threads both into the adapter, so each farm resolves its own MyIrrigation project's weather. Farms whose creds omit `project_id` fall back to the global `MYIRRIGATION_PROJECT_ID` (unchanged behaviour for Esporão/Conqueiros).

**One farm, plots spanning several MyIrrigation projects + per-plot weather (ADL / Innoliva pattern):** a farm's probes may belong to *different* MyIrrigation projects — the `external_id` (`{project_id}/{device_id}`) carries each probe's project, and probe reads are project-agnostic (they only use `device_id`). **ADL** ("Herdade das Amendoas do Lago") is one farm whose plots Castelos Norte / Falcão / Valemoura sit on projects 964 / 963 / 1162 and share one farm-level weather station. **Innoliva** is one farm, 6 plots (the "polos": Conceição/Covadonga/Fátima/Guadalupe/Rocio/Carmo, rendered as the farm-page plot tabs), 77 olive sectors — but with **per-plot weather**: each `Plot` carries its own `myirrigation_project_id` + iMetos `weather_device_id`, so each polo's sectors use that polo's own iMetos for ET₀ (Conceição has no iMetos → forecast-only). Weather resolution:
- **Weather tables** (`weather_observation`, `weather_forecast`) carry a nullable `plot_id`. `plot_id IS NULL` = farm-level weather (all pre-existing farms: Esporão/Conqueiros/ADL — behaviour unchanged).
- **Ingestion** (`services/ingestion.py` `ingest_farm`): if any of the farm's plots has weather config, fetch weather per-plot (each with its `project_id`/`weather_device_id`, stored with `plot_id`); otherwise the single farm-level fetch (`plot_id=NULL`). A device-less plot (Conceição) fetches forecast only — the observation fetch is skipped so it doesn't fall back to the adapter's global instance device. **Weather ingestion is gated on `farm.location_lat/lon` being set** — a per-plot-weather farm must still have a farm location (Innoliva onboarding sets a representative one).
- **Engine** (`engine/pipeline.py` `build_weather_context(farm_id, db, plot_id=None)`): resolves a sector's weather by its plot; falls back to farm-level (`plot_id IS NULL`); and for a farm-level caller on a farm that has **only** plot-scoped rows (Innoliva), falls back to a representative plot (the farm's most-recent-observation plot) so farm-summary / rain-skip callers still get data.
- **Adapter** weather methods take an optional per-call `project_id`/`weather_device_id` (override instance state) so one shared adapter/token serves all plots.
- **Dashboard/Boletim (UI):** `GET /farms/{id}/dashboard` returns `weather_by_plot` (`plot_id → WeatherToday`) alongside the farm-level `weather_today`, built only for plots that have plot-scoped weather rows (empty map for single-station farms — behaviour unchanged). A forecast-only plot's card fills temp/humidity/wind/ET₀ from its **own forecast** rows, never another polo's observations. On the farm page, `SectorGrid`'s `onPlotChange` callback + `lib/weather.ts` `resolvePlotWeather` make the Boletim card and the Previsão-48h strip follow the active Polo tab; plot-scoped cards say so in the header ("Boletim · hoje · <Polo>"). Note the tab default is computed inside `SectorGrid` and only written to `?plot=` on click — the page learns the initial tab via the callback, not the URL.

**Token contention caveat (Innoliva's polos share one `client_id`):** MyIrrigation invalidates a prior JWT when the same `client_id` logs in again; the adapter's `_is_client_signature_invalid` → re-auth path (fix `e107777`) self-heals each poisoned call ("ship-simple + monitor"; a shared-token-per-account refactor is the contingency if churn appears). Onboarding is a one-off idempotent script (`backend/scripts/onboard_innoliva.py`; device discovery `backend/scripts/innoliva_discover.py` → `docs/innoliva_device_mapping.csv`), not a UI.

**Archived records (2026-07-15 rule — preserve it):** `backend/app/active_records.py` centralizes active farm/plot/sector queries (`active_farms_stmt`, `active_plots_stmt`, `active_sectors_stmt`, `get_active_farm`, `get_active_sector`). All live paths — scheduler jobs, recommendation pipeline, dashboard, GDD, ingestion, calibration, alerts, anomaly detection, AI context, flowmeter rate/deviation — ignore archived hierarchy records. **Archived records remain available for historical/reporting views but must not participate in current recommendations, alerts, ingestion, or scheduled calculations.** New jobs/queries over the farm hierarchy should go through these helpers.

**Alert ownership + reconciliation (2026-07-15):** `Alert` rows carry `source` + `rule_key` (reconciliation index `ix_alert_reconciliation`; backfilled by migration `m3n4o5p6q7r8_alert_sources`). Each producer — core (`alerts/engine.py`), anomaly, flowmeter-deviation, flowmeter-flow-rate — uses its own `source` and deterministic `rule_key`s, and **reconciliation only resolves alerts owned by the producer currently running** (core cannot close anomaly/flowmeter alerts). **When adding a new alert producer, give it its own `source` and stable `rule_key`; never reconcile another producer's alerts.** Sector core-alert evaluation now runs through `RecommendationPipeline.run()`, so alerts share the exact engine state of recommendations (probe selection, calibrated soil bounds, flowmeter water accounting, rain applicability, confidence); `rain_skip_applies` is explicit in the engine result and `inputs_snapshot`. Persistent over-saturation belongs to **anomaly** — the old core over-irrigation inference from a clamped soil state is gone. Anomaly detection is scheduled after ingestion.

**Recommendation outcomes (2026-07-15):** `RecommendationOutcome` records one deterministic evaluation per accepted recommendation (`services/recommendation_outcome_service.py`): matches a manual irrigation event (preferring one linked to the recommendation) or a probe/flowmeter-detected event within **36h**; records executed / followed-skip / no-event, recommended vs actual dose, absolute+percent dose error, optional before/after VWC response. Flowmeter volume converts m³/ha → mm by ÷10. Evaluation runs after both provider and flowmeter ingestion. Creating a manual irrigation event validates that a linked recommendation belongs to the same sector (audited). Endpoint: `GET /sectors/{sector_id}/recommendation-outcomes`.

**Onboarding wizard (2026-07-15, five steps):** the frontend onboarding flow captures farm lat/lon (range+pair validated, optional elevation), sector area + optional row spacing, irrigation geometry (application rate, emitter flow/spacing — drip sectors need a known rate OR enough emitter/row geometry to derive it), encrypted MyIrrigation credentials, provider connection test + resource discovery (secret-free), project/weather-device mappings, probe `external_id`, flowmeter numeric ID + optional name — with an explicit configure-later path. API surfaces: `GET/PUT /farms/{farm_id}/credentials`, `GET /farms/{farm_id}/provider-resources`, `POST /sectors/{sector_id}/flowmeter`, plus probe creation through the frontend API client. Crop-stage contracts use a stable `key` — translated stage names are display labels, never API identifiers.

**API security (authentication + ownership):** every `/api/v1` endpoint requires a valid bearer token — `router.py` attaches `Depends(get_current_user)` to every router group **except `auth`** (token issue/register). New routers added there inherit auth automatically; don't rely on per-endpoint `current_user` params for the gate. Authorization is per-tenant via `app/access.py` `AccessController` (dependency `Access`), which resolves farm/plot/sector/probe/recommendation/irrigation_event/alert/override/water_event scoped to the caller's owned farm chain (`farm.owner_id`); **`role == "admin"` bypasses ownership** and sees all farms. Missing *and* cross-tenant resources both return **404** (no existence leak). Global catalogs (`crop-profile-templates`, `soil-presets`) stay readable by any authed user; `/audit-log` is **admin-only**. Operator/staff accounts (e.g. `you@irrigai.dev`) should be `admin`; client accounts own their own farm. Note: agronomist is *not* admin-bypassed — an agronomist owning no farms currently sees nothing.

**Startup security guard:** `config.check_production_security()` runs in the backend lifespan and `worker.main()` and **aborts boot** when `DEBUG=false` and `ENCRYPTION_KEY` is unset (would derive the encryption key from `SECRET_KEY`) or `SECRET_KEY` is still the `change-me-in-production` placeholder. A crash-looping backend behind nginx surfaces as 500s on every API call.

## Testing

- Backend tests use `pytest-asyncio` (`asyncio_mode = "auto"`). All async test functions run automatically.
- Tests under `tests/test_api/` run against test Postgres (NullPool per request) — see `conftest.py`. **Caveat:** some DB tests (`test_engine/*_db.py`, `test_api/test_crop_profile_regenerate.py`) build their own engine from `settings.DATABASE_URL`, i.e. the **dev DB** locally, not a throwaway. A test that mutates the shared globally-seeded sector (e.g. PUTs a `mad`/`field_capacity` change) **must snapshot + restore** it, or it corrupts the dev DB and breaks other suites (`test_context_loading::test_ctx_mad_in_range` reads that sector's `mad`) — deterministically, even in isolation, until you re-seed (`python -m app.seed`). CI is immune (fresh seed per run), so this only bites locally. Restore via a Core `update()` in fixture teardown (not ORM attribute-set — that trips `MissingGreenlet` in async teardown).
- **Auth in tests:** since global auth landed, data-focused fixtures override `get_current_user`. `test_api/conftest.py` exposes `client` (authenticated as the seeded owner `you@irrigai.dev`, get-or-created) and `noauth_client` (real token flow, used by `test_auth_permissions.py`). CI runs `python -m app.seed` before pytest, which creates that owner. The e2e fixture flags the seeded user `admin` in-memory for the global audit-log assertion.
- Frontend unit tests: Vitest (`npm run test:run`).
- E2E: Playwright (`npm run e2e`), requires the full stack running.
- CI (`.github/workflows/ci.yml`) runs the backend suite and `frontend-lint`; it does **not** run backend `ruff` (pre-existing project-wide `B008` on FastAPI `Depends()` defaults is not gated).

**Deploy/ops gotchas learned in the 2026-07-03 prod rollout (all real, keep in mind):**
- **`onboard_innoliva.py` is get-or-create by email for the owner User and does NOT update an existing user's password on re-run.** If the account was created on an earlier run, its password is whatever that run set — reset it with `app.auth.hash_password` (login checks `verify_password` **and** `user.is_active`). - **The `plot_id` FK on `weather_observation`/`weather_forecast` has NO `ON DELETE` rule and no ORM cascade** → deleting a Plot (or a farm's plots) is blocked by weather rows referencing them. To delete Innoliva-style data, delete the farm's `WeatherForecast`/`WeatherObservation` rows FIRST, then the farm (which cascades plots→sectors→probes→depths→readings). (Follow-up: add `ON DELETE SET NULL` to those FKs.)
- **Bulk deletes of farm subtrees deadlock with the running worker** (the scheduler ingests/recommends the same rows concurrently). `docker compose stop worker` before large deletes, then `start worker` after.
- **Migration index drops must be `DROP INDEX IF EXISTS`** — the model-declared composite indexes (`ix_weather_obs_farm_timestamp`, `ix_weather_forecast_farm_date`) existed on dev but NOT prod (dev/prod index drift), so a plain `op.drop_index` failed on prod (fixed in `6e5069f0c5fd`).

**Four invariants in this design that must not be "simplified" later:**
1. **`stale` is TERMINAL.** The partial unique index `uq_calibration_sweep_run_active` on
   `(farm_id) WHERE status IN ('queued','running')` is what makes duplicate requests impossible
   across production's `uvicorn --workers 4` — a Python pre-check races. Terminal `stale` is how a
   dead run leaves that predicate instead of locking the farm out of ever being swept again.
2. **Progress is written on a SEPARATE short-lived session.** The sweep runs in one long
   transaction; progress written on it is invisible to pollers until the end, so the bar would sit
   at 0/N for ten minutes then jump to done. `mark_running`/`record_progress`/`finish_run` each
   open their own `AsyncSessionLocal()` and commit immediately.
3. **The poll endpoint must stay un-rate-limited.** A 2s poll across a ten-minute sweep is ~300
   requests; every neighbouring endpoint carries `@limiter.limit`, so copying one would 429 the
   client mid-sweep.
4. **The per-farm lock `calibration_sweep:{farm_id}` is taken by BOTH** the drain job and the
   Monday pass, and the drain job **requeues rather than fails** when it cannot acquire — the
   request was valid, the farm is merely busy; `queued_at` staleness is the backstop.

**One finding carried into Task 5** (detail in the ledger): failed sectors `continue` before the
progress callback fires, so the progress sequence a poller sees can skip numbers, and if the LAST
sector fails no callback reports the final tally — a UI could look stalled at N-1. What covers it
is `finish_run` writing the authoritative count at the end (now via
`func.greatest(sectors_done, len(outcomes))`, so it can never lower it either). **Task 5 must keep
calling `finish_run` on every exit path, including failure.**
